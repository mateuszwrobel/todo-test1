`PATCH /cards/{id}` lands as the kanban contract's change endpoint, one card per commit (api/05 → 07 → 08 → 09): parse the body object — `title` and/or `column` — into presence-pointers for `board.Change` (a nil pointer is the contract's "field absent", so the board keeps whatever the request doesn't name), one store call, and the outcome→transport mapping at the module's single site keyed on board's typed errors with `errors.Is` — the workplan's mapping-table decision. Landed bodies, each pinned verbatim: 200 + the full four-key Card; `board.ErrCardNotFound` → 404 `{"error":"no such card"}` (api/07); `board.ErrInvalidColumn` → 422 `{"error":"invalid column"}` (api/08); `board.ErrTextRequired` → 422 `{"error":"title is required"}` and `board.ErrTextTooLong` → 422 `{"error":"title exceeds the 500 character limit"}` — both byte-identical to create's bodies (the test captures the POST and PATCH refusal bodies for the same over-limit input and requires equality: one wording per error class across verbs, the number formatted from `board.MaxTextLen` so message and rule cannot drift). Semantic rules stay board-owned; nothing is restated here.

Two body-shape decisions, both mirroring create's standing conventions. Transport class: malformed JSON, a known field present with a non-string type, and a non-numeric id are 400 `{"error":"invalid request"}` — the module's convention kept from create and the todo handlers, pinned apart from the rule refusals. Rule class: an empty object, absent keys, null values, no body at all, and well-formed JSON that is not an object all read as "no field supplied" and answer 422 `{"error":"at least one field is required"}` (api/09's stated rule). Unlike the title class — where the empty value is handed to board so its required outcome words the refusal once — the at-least-one-field clause is a request-shape rule with no carrying store outcome (`Change`'s both-nil error is an untyped programmer error), so the handler states it and `Change` is never called with two nils; nothing reaches storage.

`PATCH /todos/{id}` retires with its kanban counterpart, per the ledger: route, `handleChange`, and the todo-era test file deleted; `TodoStore` loses `Change` the way it lost `Create` at api/02 (the port declares what its handlers use — `List` and `Delete` stand until the deletion retires). One behavioral note on the retirement pin, beside api/02's note on the `/todos` pins: there the whole path lost every method, so the pin answers 404; here **DELETE /todos/{id} survives on the exact same path pattern**, so ServeMux matches the path and only the method goes unmatched — the router's true answer is 405 with `Allow: DELETE`. `TestPatchTodosRetiredServes405DeleteStillOwnsPath` pins that answer, the Allow header, and that the todo store is untouched.

Composition followed the route: `cmd/todo` gains the `/cards/` subtree mount (the exact `/cards` mount only reaches POST, so item paths would otherwise fall to the page catch-all — same shape as the `/todos/` mount), and the shutdown in-flight test rides the retired endpoint's replacement: a board card created over POST, then a genuinely half-sent `PATCH /cards/{id}` whose durability probe reopens the board store. `board`, `todos`, `ui` untouched; `BoardStore` gains `Change` — structurally satisfied by `*board.Store`, so the composition root needed no wiring change.
