# KW5 ui — drag between columns, reorder persists, abandoned changes nothing

Base: main @ 36ee746 (kw5 api landed — PATCH /cards/{id} carries column+position).

## What is landing

Drag-and-drop as the page's only movement mechanic (workplan decision), three
cards sharing one machinery, landing 08 → 09 → 10:

- `ui/move.go` — the move fragment endpoint (`PATCH /ui/cards/{id}/move`): one
  accepted drop = one upstream `PATCH /cards/{id}` with `{"column", "position"}`
  over real HTTP; answers the fresh board-area fragment (server truth, swap not
  reload), mirroring the contract's 404/422 states through the already-shipped
  failure arms (missing-card banner; reason-at-the-card) — no second mechanism;
  the shared stale surface stays card ui/11's.
- `ui/render.go` — every card draggable; the shell's script block gains the
  HTML5-DnD drag handler (htmx-independent): dashed source slot, between-card
  drop indicator, drag chip carrying the title, one `fetch` site per accepted
  drop, zero-request abandonment legs.
- `ui/static/style.css` — drag-state visual rules on existing tokens only.

## Verdict recorded from card ui/10

Same-position drop (drop onto the source slot / source column at the card's own
index) is **one real request**, not a client-side no-op: the card defines
abandonment as dropping *outside any valid target* (or releasing without a
drop); a slot drop is a drop on a valid target, so it rides card ui/08's
one-request rule and the server's re-normalized truth comes back unchanged.
The client computes the payload; it does not second-guess accepted drops.

## Position math

Contract position = index within the target column AFTER removal (board.Move
removes before inserting, same-column included). The client's `dropPosition`
counts the rendered cards ahead of the insertion line in the target list, not
counting the dragged card's own slot — the after-removal index read off the
DOM the user sees, so indicator and request can never disagree.
