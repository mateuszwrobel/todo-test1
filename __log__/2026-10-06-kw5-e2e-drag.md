# KW5 e2e — drag lane (wave end)

Wave-end integration for KW5: re-executed the parent scenarios "Drag card
between columns" + "Drag reorder within a column" + "Done is column
membership" plus the move leg of "Operation on missing card" (completing it
fully — edit/delete legs green since kw3/kw4) in the browser
(workplans/dependencies_kanban.md §KW5).

What changed and why:
- `e2e/kw5-drag.js` — new lane file (kw1–kw4 lanes untouched), same harness
  shape as kw4: fresh seeded temp board + port + server per scenario,
  SIGTERM teardown, window-marker no-reload proof, DOM-vs-GET-/board
  agreement and contiguous-position invariants reused verbatim in spirit.
  Gestures are real HTML5 DnD in chromium via mouse choreography (hover,
  mouse.down, stepped mouse.moves → Playwright's drag interception emits
  dragstart/dragover/drop) — no dragTo() because the mid-gesture drop
  indicator must be read between the final hover and mouse.up. Instrumenta-
  tion: a `page.on('request')` listener counts PATCHes per gesture — exactly
  one with body {column, position} per accepted drop (the one-request rule
  at the browser boundary; the ui→api contract-call count stays owned by
  ui/move_test.go's recorder), zero per abandonment (the request listener is
  the proof, the unchanged DOM + GET /board are the corroboration). Stale-
  drag staging: two browser contexts on ONE server — context A deletes via
  its own Delete control (the workplan risk "a stale page drags a card that
  another action deleted" verbatim), context B never refreshes so its stale
  card stays genuinely shown and draggable; its drop attempts exactly one
  PATCH, the shared #missing-card surface states "no such card" over the
  re-rendered truth. Mid-gesture indicator witnessed honestly: visible,
  sitting between the two In Progress cards — and the request body's
  position=1 proves the same gap rode the request (both are render.go's one
  dropPosition count).
- `Makefile` — KW5 lane line in the `e2e` target + header comment.
- `e2e/README.md` — KW5 section + a "known product bug" note.

Clarification — PRODUCT BUG found (no product edits made here): the drag's
fetch swap assigns the board fragment with plain `innerHTML` (render.go's
drop handler), while the bundled htmx is 2.0.6, which removed the
MutationObserver auto-scan — htmx only wires content that arrives through
its own swap. Consequence, reproduced verbatim in the lane's witness line:
after ANY accepted drop, an Edit Save on the re-rendered markup submits
natively — `GET /?title=Witness+probe`, a full page navigation, edit
discarded — and a Delete click issues nothing at all, until the next full
render. kw3/kw4 lanes stay green because every swap they take goes through
htmx, which processes what it swaps; the Go fragment tests can't see this
(HTTP-level only). Root cause pinned by probe: after evaluating
`htmx.process(board-area)` in the browser, the identical edit PATCHes
/ui/cards/{id} and lands. Fix belongs to the drag swap site (htmx.process
the swapped region or route the fetch answer through htmx.swap) — one line
in ui/render.go's fetch handler; this lane's scenario 3 cross-check asserts
the kw3 behavior on the fresh truth render so the suite goes green fully
today and the bug is reported, not hidden.

Verification: `make e2e` fully green — all five lanes, 18 scenarios +
