Live-reproduced defect, fixed at the guard. The one-time migration asked "does the board hold any cards?" as its once-switch, so a user who imported at first start and later deleted every card restarted into a resurrection: the emptied board re-answered "never created", `todos.db` was still there, and the deleted todos came back as fresh-identifier cards — breaking "Existing todos import once, at first start" (parent plan decision) and card server/02's "the import does not run twice". Neither workplan wording could carry the guard: schema-existence is unimplementable because `board.Open` commits the schema before the import decision runs (an interrupted import would strand forever, violating card server/05's completes-next-start), and the emptiness substitution built on that rejection is exactly what this repro breaks. The rejected alternative — a meta marker row — is now adopted, recorded in the amended plan decisions.

**What changed and why.**

- **`board/store.go` — the marker becomes board state.** The schema gains a `meta(key, value)` table created with the cards table, and two small exported ops: `Imported() (bool, error)` (presence of the marker row; absence is the false answer, not an error) and `MarkImported() error` (idempotent record of the decision without placing cards). `Import` now writes the marker **inside its own transaction**: landed import = recorded import, refused/rolled-back/stopped import = nothing recorded — so the retry arm card server/05 states survives the marker semantics, and no card mutation (Delete included) can ever rewind the record. Validation and all-or-nothing semantics are untouched; the empty-batches no-op still writes nothing, marker included. Verdict on the open design choice: `Import` does NOT refuse when the marker is set — the guard is startup policy and stays in the composition root (one owner, principle 8); refusing would hand the insert primitive a second reason to change and protect no window that exists, since the marker commits atomically with the cards and the single-process start sequence reads the guard before reaching Import. A repeat import appends per contract and leaves the record set (pinned, not implied).
- **`cmd/todo/migration.go` — guard = `store.Imported()`, replacing the List-emptiness loop.** Marker on record → the source is past evidence, whatever the board holds. No marker → first-ever decision: source present → read/map/`Import` (cards + marker in one commit); absent → nothing to import. Every first decision ends with `MarkImported()`, idempotent after a landed import and the decision's whole trace otherwise — so a source appearing after a no-import first start stays ignored (the server/02 guard arm keeps holding), while the loud-failure path never reaches the line (import error → startup dies → unmarked board retries).
- **Tests.** New resurrection pin `TestDeleteAllAfterImportRestartDoesNotResurrectTodos` (cmd/todo migration harness): import at first start, DELETE every card through the contract, restart with `todos.db` still present → all three columns empty, no fresh-id copies, source bytes unchanged. Board-level marker pins (`board/store_marker_test.go`): fresh answers not-imported; landed import marks and survives reopen; refused and no-op imports mark nothing; MarkImported idempotent, card-state-free, reopen-durable; repeat import with the marker set still places; marker survives deleting every card. Existing migration/interrupted tests pass unchanged in their assertions and their comments now speak marker semantics (the interrupted one names the unmarked board as what licenses the retry).
- **e2e kw6 scenario 2** extended with the delete-all legs in the lane idiom: every imported card removed through the page, one more restart with the fixture still present, then all three columns state their emptiness, `count(*) FROM cards` is zero, and the fixture hash is still unchanged.
