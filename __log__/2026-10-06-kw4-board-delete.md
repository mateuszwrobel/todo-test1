The Delete operation of the board store contract lands, one commit per card, in dependency order (11 → 12). What changed and why:

- **One operation, reuse over new machinery** — `Delete(id int64) error` is the store's third mutation, built on exactly the pieces Change already established: `Begin` + `defer tx.Rollback`, an existence read, and the existing `renormalize(tx, col)` helper as the gap-close step. No new invariant machinery — the workplan's "remove and renormalize the card's column in one transaction" line became three statements plus the shared error mapping. Deleted-card gap close and Change's source-column gap close now share one implementation, so the contiguity invariant has one code path per direction out of a column.
- **Existence check before DELETE, quote order** — inside `Delete`, the `SELECT "column" FROM cards WHERE id = ?` read is the transaction's first statement and strictly precedes the `DELETE`; its miss maps `sql.ErrNoRows` to `ErrCardNotFound` and returns before any write statement executes. The read does double duty by design: the column it reports is renormalize's target (the gap the departure opens), and its miss is the named store outcome — the same ordering Change uses, so a rejected delete provably touches nothing. Verified against this commit's store.go.
- **No id reuse** — the schema's `integer primary key autoincrement` (board/01, ADR-002 conventions) already guarantees monotonic ids across deletes; the pin is a test, not code: create → delete → create, later id strictly greater than the deleted card's, and the track keeps moving for the next create too. `ErrCardNotFound`'s doc now names both reporters (Change and Delete) instead of Change alone.
- **Unknown-id reporting is general, not a value** — board/12's table aims the delete at zero, a negative, one past the highest live row (the existing `unknownID` helper), one far past it (`+ 1<<40`), and an already-deleted card — the gone card is an unknown card, and its board is pinned against what the first delete left. Each row pins cell-for-cell `List` equality plus the autoincrement counter (`sqlite_sequence.seq`, via `lastIssuedID`) untouched: a rejected delete issues no INSERT, so the next accepted create carries exactly the next id. The counter is read instead of max-live-id because the deleted-twice fixture may have removed the highest row.
- **Delete really removes** — one integration-ish subtest pins the gone-ness across the contract: `Change` targeting a deleted identifier answers `ErrCardNotFound` with the zero Card and the delete's result unchanged cell-for-cell.

Rows cover: middle/top/bottom of three, a column's only card, in_progress and done deletes behaving identically, and every row pinning the untouched columns cell-for-cell.
