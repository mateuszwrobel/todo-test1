**Styling — what changed and why.** `ui/static/style.css` (embedded via the existing `//go:embed static`, served at `/static/style.css` like htmx.min.js, linked from the page shell) carries the whole design language from the six mockups: grey page bg, centered white card, create row above a bordered list panel with thin row dividers, big accent-blue checkboxes, grey strikethrough done titles (keyed off the existing `data-state` attributes — never off text), grey secondary Edit/Delete/Cancel vs blue primary Add/Save, red inline error text, the pink missing-todo banner above the list, and bordered centered empty/failure panels with a button-styled Retry. No transitions or animations anywhere, and no selector depends on rendered text — ids, `data-state`, and classes are the only anchors, so the behavior-frozen wording can never shift a pixel rule.

Two layout problems solved without touching the frozen DOM:

- Mockups put the create row above the list; the DOM order (`#todos-area` first, create area after) is the frozen region-swap structure. Flex `order` on `main`'s children fixes the visual order only — DOM untouched.
- The open edit band needed a full-width second line (mockup 04), but the reveal rule lives in the page shell's inline `<style>` (`li.editing .edit-form{display:inline}`, behavior, untouched). The stylesheet wins by specificity, not by editing the shell: the `#todo-list`-prefixed rule restyles only the already-revealed band (flex: input + Save + Cancel), and `order` pulls the row's Delete up to the first line.

**Design deltas chosen (mockups are approximate; contract/journeys are truth):** every pre-existing rendered string stays — placeholder "What needs doing?", "No todos yet.", "Could not load todos.", banner/contract reasons — so the e2e text assertions hold verbatim. The one text delta is the heading "Todos" → "My Todos" (named explicitly in the design brief, asserted by no unit or e2e test; the `<title>Todo</title>` stays). The mockups' "Add a new todo..." placeholder and longer empty/failure wording were NOT adopted for that reason. The grey hint "Up to 500 characters" is added static wording matching the contract (todos.MaxTitleLength = 500, message wording "title exceeds the 500-character limit"); the ui boundary forbids importing todos and no discovery endpoint exists, so a template value from the constant is impossible — documented drift risk: if the limit ever changes, this line and the contract must move together. The rows' existing "done"/"not done" state words stay in the DOM (text frozen, still read by assistive tech) but render visually-hidden, since the mockups make the checkbox the sole done indicator.

**Story gallery — production-compiled test support.** `ui/stories.go` renders one page per the ui workplan's state list: seven sections with stable containers `#state-list-populated`, `#state-empty`, `#state-create-error`, `#state-edit-band`, `#state-load-failure`, `#state-missing-todo`, `#state-in-flight-disabled`, each captioned `state: …`. Every section body is the REAL surface template executed against deterministic in-code fixtures — the same `listTmpl`/`emptyTmpl`/`failedTmpl`/`bannerTmpl`/`createAreaTmpl` the fragment endpoints use, so the gallery cannot drift from production markup. It is production-compiled (it is a served page) yet test-support-shaped: no store/api access anywhere in the render path (a unit test proves an api request never occurs), no clock, no randomness. The fixture list (Buy milk / Pay electricity bill done; Walk the dog / Read 20 pages not-done; edit band prefilled "Walk the dog in the park"; contract wordings "title is required" and "no such todo") is fixed at compile time. The in-flight section renders the real create + list fragments and marks exactly card ui/16's four controls (Add, checkbox, Save, Delete) with the plain `disabled` attribute; the string replacements target the templates' rendered control markup and the unit test pins each result, so template drift fails a test instead of silently un-disabling the gallery.
