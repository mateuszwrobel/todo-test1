What changed and why:

- The store grew the frozen-done rule as a typed outcome (`todos.ErrDoneFrozen`)
  checked in `Change`'s title direction — a pre-read of the row's done column
  before any write, so a refused edit leaves the file untouched and a missing
  id still surfaces as not-found. Chosen over a post-write rollback because the
  store workplan's data-flow clause demands the refusal precede the column
  write. Validation of the new title (trim, limit) runs only after that check:
  done-ness dominates an invalid title, since the todo cannot be edited at all.
- The api change handler maps the store's typed outcomes to the frozen JSON
  contract; the frozen-done mapping is a 422 with the contract wording, kept in
  its own card-sized hunk so sibling lanes touching `api/change.go` (W7) stay
  conflict-free.
- The UI needs no new endpoint: the existing `PATCH /ui/todos/{id}` dispatches
  on whether the form carries a `title` field, so the edit band reuses the same
  fragment pipeline as toggle and delete. The refusal path relies on the page's
  `htmx:responseError` listener because htmx 2 never swaps 4xx bodies by
  default — the listener swaps only HTML-bodied refusals into `#todo-list`,
  so plain-text error bodies can never render as a row. The render model gained
  one per-row struct (`listRow`) carrying the stated reason and the typed text,
  keeping the template honest: the row the fragment draws is server truth
  (a todo that became done shows done, with no edit control offered).
- The e2e harness (`make e2e-w4`) proves the wave in a real browser — including
  the stale-page case, driven by marking a todo done through the JSON contract
  while the page still shows it editable. It asserts exactly the card wording
  and nothing more: an early draft asserting focus-on-open was cut, since no
  ui card asks for focus.
