The Change operation of the board store contract lands, one commit per card, in dependency order (08 → 09 → 10). What changed and why:

- **One operation, two directions** — `Change(id int64, title *string, column *Column) (Card, error)`: a nil direction is untouched, at least one must be non-nil (a call with neither is an argument error before anything else). One transaction per call; everything it writes — rename, placement, gap close — commits or rolls back together, matching the workplan's torn-ordering mitigation.
- **Title direction, same rule source** — the candidate text runs through `validateText`, the exact function Create screens through, so blank/over-long changes get the same `ErrTextRequired`/`ErrTextTooLong` typed outcomes as creates and no entry point can drift from the rule. The trimmed text is stored. A title-only change touches only the title column of the row: place and identity survive — column, position, id — pinned cell-by-cell through `List` (every other card on the board must compare equal, so neighbor drift fails the test). Done-column cards are fully editable — the done row in the table pins that no frozen state exists anywhere, per ADR-003's column-membership-is-done decision.
- **Validation before write, quote order** — inside `Change`, the `validateText` call and the `validColumn` guard are the first statements after the both-nil argument check and strictly precede `s.db.Begin()`; the existence read is the first statement inside the transaction and precedes every UPDATE. So no rejection — text, column, or missing card — ever executes a write statement. This is the same ordering Create uses (validation before `db.Begin()`) carried to the new operation; the board-unchanged + next-id tests pin it observably.
- **Not-found reporting** — `ErrCardNotFound` maps the miss of the existence read; the board is pinned cell-for-cell identical (`List` equal before/after) for every direction combination and no identifier is consumed — Change issues no INSERT, so the next accepted create carries exactly the next id.
- **Enum guard** — `Column` is a string type, so callers can hand the store anything; `validColumn` screens the fixed enum (`todo`, `in_progress`, `done`) before Begin and a miss reports `ErrInvalidColumn` — never a storage-constraint failure, the guarantee the schema comment demands, now covering the column direction the way `validateText` covers text. Values tested: empty, wrong case, padded, hyphenated, junk.
- **Column move — minimal on purpose** — a valid column change moves the card to the BOTTOM of the target (position = target size before the move) and closes the gap in the source via `renormalize(tx, col)`, which rewrites one column's positions to contiguous 0..n-1 in current order inside the caller's transaction (the workplan's renormalize-in-every-mutation invariant as a reusable step; board/11's Delete will close gaps with it too). **KW5 note: neighbor-ordering semantics — index placement on cross-column moves and same-column reordering — are the dedicated cards board/06 and board/07; this is bottom-append only, and a same-column request deliberately places nothing so board/07's behavior is not invented early.** The note is repeated in the board/10 commit message and the Change doc comment.

Tests (`board/store_change_test.go`) derive from the three cards' Gherkin as tables over the general contract in the existing style, reusing the `columnFixture`/`seedBoard`/`placeCard` fixtures from the list tests. No api/, ui/, cmd/ or todos/ changes — the PATCH surface maps these outcomes in api/05/07/08 later in the wave.
